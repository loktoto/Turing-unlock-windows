# Pinned upstream research

Research basis: [TU102 upstream](https://github.com/nlzy/turing-unlock/tree/417f333263ff169e8f449c931b70db9dfd7b8ef4) at `417f333263ff169e8f449c931b70db9dfd7b8ef4`, and [Windows platform reference](https://github.com/impacifist/Windows-GPU-UNLOCK/tree/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e) at `5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e`. [UPSTREAM_LOCK.md](../UPSTREAM_LOCK.md) records source hashes and licensing. The Windows project is a reference, not an imported implementation. These observations describe source behavior, not proof that it is safe on an unknown machine.

## TU102 execution and host boundary

- [`unlock.c` entry](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/unlock.c#L601-L707) obtains six firmware inputs, sets 32-bit DMA masks, parses the booter, ELF image and boot descriptor, and validates BAR/configuration before mapping the device. The files' sizes and geometry checks do not establish their origin or authenticity. The current host library has no firmware acquisition or device adapter.
- [Entry state and layout](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/unlock.c#L709-L783) inspect WPR and boot state; an existing WPR or completed boot triggers a pre-fire FLR, then framebuffer readiness and GFW are polled before constructing layout. The layout depends on live values and assumptions; a valid calculation is not proof those inputs or the profile are correct.
- [FWSEC](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/unlock.c#L248-L364) reads the PROM through BAR space, accepts descriptor version 2 for execution, patches the FRTS command, constructs DMA buffers and runs a GSP loader; success checks scratch and WPR state. The local parser accepts more formats for inspection; that does not authorize executing them.
- [Main sequence](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/unlock.c#L785-L867) enables bus master, runs FWSEC, resets GSP, prepares booter/signature/metadata/boot and radix DMA, starts SEC, checks PLM and selector/readout results. This is TU102-specific device execution, not a read-only diagnostic.
- [Cleanup](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/unlock.c#L566-L599) clears bus mastering, performs FLR and checks PCI transaction pending in the reset path. [The exit path](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/unlock.c#L868-L880) invokes it on error after firmware started and retains DMA if quiescence is not established. There is no unconditional post-success FLR. The upstream quiescence bookkeeping is a Linux implementation assumption, not independent proof for UEFI; reset success alone must not release potentially visible DMA or permit handoff.

The portable candidates are bounded byte parsing and layout arithmetic: [VBIOS descriptor parser](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/vbios.c#L218-L278), [layout](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/layout.c#L41), [ELF and radix planning](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/prep.c#L57-L138), and [boot descriptors and readiness predicate](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/boot.c#L11-L70). The current boundary and local changes are enumerated in [API_MAP.md](API_MAP.md). Mutation-oriented [FRTS patching](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/vbios.c#L279) and [metadata/radix packing](https://github.com/nlzy/turing-unlock/blob/417f333263ff169e8f449c931b70db9dfd7b8ef4/kernel/turing_unlock/prep.c#L139) remain excluded; reintroduction needs separate review and validated inputs. Firmware binaries are not supplied or redistributed here.

## Windows platform lessons and limits

[port.c](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/unlock/port.c#L74-L120) separates CPU pointers, device addresses, mapping handles and allocation lifetime; partial or failed mappings and failed cleanup must be handled. Its requirements such as a nonzero, aligned, 32-bit device address are that profile's policy, not universal EFI facts. [MMIO/config access](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/unlock/port.c#L121-L163) uses BAR bounds and latched faults. [Bus-master control](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/unlock/port.c#L167-L257) tracks an attempted external change before making it, checks readback and retains resources on uncertain cleanup. These patterns inform a future contract, but are not a TU102 adapter.

[app.c GOP enumeration](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/unlock/app.c#L59-L123) illustrates that console and physical GOP handles can be related; [PCI discovery](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/unlock/app.c#L200-L214) requires a unique match. Its fixed topology and board checks are profile-specific. An incomplete ownership graph or ambiguous association must remain unknown. The [compatibility matrix](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/docs/COMPATIBILITY.en.md#L1-L22) reports exact Ampere systems and limits; its [headless guide](https://github.com/impacifist/Windows-GPU-UNLOCK/blob/5c98f11eaafdcb7a2a06fb14fcdcde7297eb409e/docs/HEADLESS.en.md#L1-L19) explicitly limits its result. Neither demonstrates TU102 handoff or compatibility. Headless is a separate ownership and recovery problem, not evidence that lack of a visible display makes a reset safe.
